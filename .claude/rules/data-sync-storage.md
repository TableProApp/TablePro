# Storage, sync and the database core

This path holds user data. A silent wrong answer here looks exactly like an empty database, so prove late-completion and cancellation behavior with a test.

- **A synced CKRecord type or field reaches CloudKit Production before anything writes it.** Both apps pin the container to Production, where nothing is auto-created, and CloudKit rejects a whole record that carries an undeclared field. Write fields only through `record.fields(SomeSyncField.self)`, never `record["..."]`. To ship one: add it in Development, deploy to Production in the Console, run `apple/scripts/export-cloudkit-schema.sh`, commit `apple/CloudKit/production-schema.ckdb` and the core's copy the script writes beside it, then add it to the matching `verifiedInProduction` and mark it deployed in the core's registry (`core/crates/records/src/cloudkit/registry.rs`). `ProductionSchemaParityTests` checks code against the snapshot in both directions, not against the server, so never edit the snapshot by hand: `apple/scripts/export-cloudkit-schema.sh --check` compares it with Production. A tag's `app` job runs `--check-deployed` instead, which fails only on a record type, field, field type, index, role or grant the tag's snapshot has and Production lacks.
- **A storage format stays readable by the previous stable.** Sparkle never downgrades, and a beta user can turn betas off (`apple/RELEASING.md`, Storage check). The one exception is a value the previous stable has no field for, such as a theme color in a slot added after it: that file and its synced record are written at the oldest schema that holds it, and everything else keeps the old format (`.claude/rules/theme.md`, Model and Sync).
- **iCloud runs on the core engine** (core ADR 0054, The Apple apps on the engine). The engine owns bases, standing, held and deferred sets, merges, retries and the change token, and its rules for records this build cannot read, Local only connections, categories that are off, full fetches and removed zones are the core's (0054, Rules for both providers). `SyncProviderCoordinator` only decides whether iCloud runs and asks for passes; `CloudKitCoreTransport` maps CloudKit and decides nothing. A store still never re-encodes or writes over a record it cannot decode (a save carrying its id is refused), and an import treats its id as taken.
- **Journal after the write.** Each store the Mac still keeps in Swift calls `SyncHostJournal.recorded` with the ids its write saved and removed, once the write landed. The engine's diff decides what goes up, so a missed call only delays a push (0054, The engine; 0060). A store never marks a record dirty or tombstoned itself.
- **The downgrade mirror owns the Swift engine's metadata.** While the previous stable runs the Swift engine, `LegacySyncMetadataMirror` writes what that build reads after every committed pass, the change token last, and marks the ids of each journal write, both as the engine hands them over (0054, Downgrade mirror). A quit waits, bounded, for the marks of every write told so far (`SyncProviderCoordinator.flushBeforeQuit`). Nothing else writes the token, the dirty and tombstone keys, standing, the held and deferred sets or `SyncRecordCache`, or the engine reads that as the previous stable having run and imports them again. The format stays the one `SyncMetadataStorage` and `SyncRecordCache` read in that build.
- **Concurrent schema loads await the one in-flight `loadTask`** in `SQLSchemaProvider`; never guard with a flag that returns without data.
- **Every metadata read goes through `DatabaseManager.withMetadataDriver`**, never `MetadataConnectionPool.shared` directly, so an embedded engine with `supportsConnectionPooling = false` (DuckDB, PGlite) stays on its session driver; a second connection to it is a different, empty database.
- **A capability with no `DriverPlugin` static is curated per type**, and `buildMetadataSnapshot` must carry it over from the built-in snapshot, or plugin registration resets it to the default.
