# 0011: TablePro accounts live in the core, with features gated by the entitlement

- **Status**: Accepted
- **Date**: 2026-11-05

## Context

TablePro's licensing moved to accounts on tablepro-cloud, whose `docs/design/clients.md` is the spec for every app. An app signs in through the browser with OAuth, registers its machine as a device, and holds an entitlement: a JWS signed with Ed25519 that lists the feature codes the account's licenses unlock. The macOS app moved to it in #4045. On 2026-11-05 the maintainer decided the Linux app is licensed as the Mac is, built now, while the paid features come to Linux later. The Windows app will take the same flow, and the Mac can move onto the core per [0010](0010-macos-on-the-core.md).

clients.md gives Linux the `/v2` flow only, since it had no licensing to migrate: the public client `tablepro-linux` with a loopback redirect on any port (RFC 8252 section 7.3), the device platform `linux`, and no license key exchange.

## Decision

`core/crates/account` (`tablepro-account`) does what the macOS `Account` service does, without a GUI and without a platform service: sign-in and sign-out, the tokens, the device, the entitlement, the refresh schedule and the gate. It depends on `core` and `storage`. Each app passes in what its platform does its own way:

| Seam | Linux app |
| --- | --- |
| `RefreshTokenVault` | the keyring item `account_refresh_token`, through `tablepro_linux_platform::SecretStore` |
| `BrowserLauncher` | `gtk::UriLauncher` |
| `MachineId` | `MachineId::derive` of the text `tablepro_linux_platform::read_machine_id` reads |
| `AppClient` | `AppClient::LINUX`: client `tablepro-linux`, platform `linux` |
| `AccountSettings::account_file` | `account.json` in the state directory |

## How it works

- **OAuth.** `oauth2` 5 with PKCE (S256) for the authorization URL, the code exchange and the refresh, sent through the workspace's reqwest 0.13 with redirects off; rustls on aws-lc-rs with rustls-platform-verifier ([Linux ADR 0009](../../../linux/docs/decisions/0009-crypto-provider-and-sources.md)). Scopes `openid email offline_access app`. The redirect comes back to a listener on `127.0.0.1:0` that serves requests until one carries this sign-in's `state`. The authorization URL carries `machine_name`, `app_version` and `os_version`, the values the device is registered with. Revocation (RFC 7009) is a form POST of our own: oauth2 refuses a revocation endpoint that is not https.
- **One sign-in at a time.** Each sign-in and sign-out moves a counter. A sign-in whose browser comes back after a later one, or after a sign-out, has its tokens revoked, never adopted. Cancel ends only the wait for the browser: once the code is back, its tokens are stored. A sign-in whose answer has no refresh token replaces nothing.
- **Tokens.** The access token lives in memory until its expiry on the wall clock, since `Instant` stops while the machine sleeps; a 401 drops it, so the next call refreshes it. The refresh token lives in the vault. When no vault takes it, it stays in memory and the next launch starts signed out. One operation holds the session at a time, so a refresh is single-flight.
- **The `/v2` client** is generated by progenitor 0.15 from tablepro-cloud's `api/v2.openapi-3.0.json`, copied into `openapi/`. Every enum in an answer is a string, so a value this build does not know still reads. An answer that does not match the document is reported by where it stopped matching, never with its body, which can hold the entitlement or the account's details.
- **Machine ID.** Linux's is HMAC-SHA256 of the 16 bytes `/etc/machine-id` holds, keyed with `app.tablepro.TablePro`, as 64 lowercase hex characters (clients.md, Linux): machine-id(5) asks that the ID never be sent as it is, only hashed with a fixed application-specific key. The crate derives it; the platform reads the file. Flatpak binds the host's `/etc/machine-id`, or D-Bus's `/var/lib/dbus/machine-id` where there is none, into every sandbox at `/etc/machine-id` (`flatpak_run_setup_base_argv` in `common/flatpak-run.c`), and the host build reads the two in the same order, so the installed app and the Flatpak are one device.
- **Device and entitlement.** After a sign-in: `POST /v2/devices`, a refresh so the access token names the device, then `POST /v2/devices/{id}/entitlement`. A refresh that fails after the registration leaves no token behind, so the next try gets one that names the device. The device ID and the entitlement go to the account file. The entitlement is refreshed at launch and after a sign-in; 24 hours after a refresh that worked, an hour after one that failed or met the device limit, counted from the last refresh whatever asked for it, on the wall clock too, so one that came due while the machine slept runs within five minutes of the wake; when the app comes back while past the limit; on Refresh or Try Again; and after a device is removed (clients.md, Shared rules). A 429 holds that call until its `Retry-After` has passed on the wall clock.
- **Verification.** `jsonwebtoken` 11 on aws-lc-rs checks the EdDSA signature with the key for the token's `kid`, and `aud`. `alg`, `typ` and `kid` are read from the header by hand first, and `mid`, `nbf` (300 seconds of leeway) and `exp` against the caller's clock after. The public keys ship in `entitlement_keys.rs`, by the RFC 7638 thumbprint of each. The checks run against tablepro-cloud's shared vectors. An entitlement kept on disk that has expired is read back as it was before it expired: it still says who has paid, as macOS keeps it, and only its features stop.
- **Gate.** `AccountStatus::feature_access(code, now)` answers `Available`, `SignedOut`, `NotIncluded`, `Expired`, `RefreshFailed` or `DeviceLimitReached` from the feature codes only; an app knows no plan or tier.
- **Errors** carry a stable `code()` (`account.device_limit_reached` and the like); each app words them.

## Consequences

- Linux has none of the ten paid features yet, so nothing is gated: a feature that comes to Linux asks `AppServices::feature_access` with its code.
- Another app adds its `AppClient` once tablepro-cloud registers its client and platform; the macOS client's redirect is a custom scheme this crate does not listen on.
- Windows reaches the account through `ffi` when it adopts it, with a `RefreshTokenVault` over its Credential Manager store.
- `linux/build-aux/update-cloud-api.sh` copies a newer `/v2` document and the vectors in; `/v2` only grows, so an older copy keeps working.

## Alternatives considered

- **`linux/crates/account`, as clients.md first named it.** Nothing in the crate is Linux's own once the keyring, the browser and the file read come in from the app, and the Windows app needs the same flow.
- **`SecretItem::AccountRefreshToken` behind the core's `SecretItems`.** It changes the FFI's `SecretItemTag` and the Windows bindings before Windows uses the account; the trait is the smaller seam until then.
- **The systemd app-specific ID as it is (`sd_id128_get_machine_app_specific`).** It keys the HMAC with the machine ID and keeps 128 bits; the server takes 64 hex characters.
- **A hand-written `/v2` client.** clients.md asks for generated clients only.
