# TablePro issue review, 2026-10-20

This is a dated comparison of TablePro's GitHub issue tracker with BookiE at `84f03a0385562d97554c47a06e6cebab189c3004`. It records transferable failure patterns and current BookiE follow-up candidates. It is not a claim that every issue body was independently reproduced.

## Scope

The GitHub issues API returned 983 issues at review time: 117 open and 866 closed; 398 carried the `bug` label, of which one was open. The open list was dominated by feature requests. The review enumerated the issue records and examined the PostgreSQL, performance, test strategy, export, SSH and representative closed-bug reports most relevant to BookiE. Counts are a dated snapshot and will change.

Representative reports reviewed include [#3599](https://github.com/TableProApp/TablePro/issues/3599), [#3605](https://github.com/TableProApp/TablePro/issues/3605), [#3606](https://github.com/TableProApp/TablePro/issues/3606), [#3608](https://github.com/TableProApp/TablePro/issues/3608), [#3619](https://github.com/TableProApp/TablePro/issues/3619), [#3658](https://github.com/TableProApp/TablePro/issues/3658), and [#3660–#3667](https://github.com/TableProApp/TablePro/issues/3660). Closed reports used as boundary-test examples include [#216](https://github.com/TableProApp/TablePro/issues/216), [#1247](https://github.com/TableProApp/TablePro/issues/1247), [#1345](https://github.com/TableProApp/TablePro/issues/1345), [#2012](https://github.com/TableProApp/TablePro/issues/2012), [#2242](https://github.com/TableProApp/TablePro/issues/2242), [#2339](https://github.com/TableProApp/TablePro/issues/2339), [#2934](https://github.com/TableProApp/TablePro/issues/2934), [#3103](https://github.com/TableProApp/TablePro/issues/3103), and [#3316](https://github.com/TableProApp/TablePro/issues/3316).

## Lessons that transfer

| TablePro pattern | Why it is useful | BookiE status and action |
|---|---|---|
| pgvector `vector`, `halfvec`, `sparsevec` need distinct handling; values can be large ([#3599](https://github.com/TableProApp/TablePro/issues/3599)). | Extension values need an explicit exact-value, preview, and size-bound contract. Similar names do not establish the same wire type. | The PostgreSQL research already records these as unqualified extension cases and distinguishes pgvector from PostgreSQL's built-in `int2vector`/`oidvector` ([research review](2026-10-15-postgresql-client-research/review.md)). Keep unsupported values visibly undecodable; do not coerce to NULL. Qualify a type and consumer path before adding rich display or editing. Large values must respect existing materialization/preview bounds. |
| Large catalogs require measured budgets ([#3660](https://github.com/TableProApp/TablePro/issues/3660)). | Schema/table counts alone do not reveal main-loop stalls, repeated metadata work, or memory growth. | Already owned by BookiE [#580](https://github.com/cozyGarage/BookiE/issues/580), which covers PostgreSQL many-schema filtering and catalog performance. Extend that acceptance with representative scale (for example 100 schemas × 500 tables), first-load/search/completion latency, main-loop responsiveness, and memory. Do not create a duplicate issue. `docs/known-limitations.md` also records that hiding schemas does not currently reduce catalog query work. |
| Round-trip tests should cover values through user-visible paths ([#3665](https://github.com/TableProApp/TablePro/issues/3665), [#3666](https://github.com/TableProApp/TablePro/issues/3666), [#3667](https://github.com/TableProApp/TablePro/issues/3667)). | Correct decoding alone does not prove export, import, ordering, truncation, and type preservation agree. | BookiE already has broad per-type, wire, CSV and export tests, including PostgreSQL-specific contracts. A full UI export→import→row-checksum scenario is not evident. Adapt this idea only to supported paths: CSV import exists, while full-table export is explicitly refused by [ADR 0014](../decisions/0014-full-table-export-snapshot.md). Do not promise XLSX/JSON re-import. |
| Cross-product policy tests for each write entry point ([#3663](https://github.com/TableProApp/TablePro/issues/3663)). | A new tool can accidentally bypass one of token scope, connection allowlist, policy, safe mode, or terminal audit. | Existing policy/MCP/release tests are substantial. A useful guard is a coverage matrix for every externally reachable write path, including denied cases and terminal audit outcomes. Treat this as test-structure inspiration; this review did not find a specific BookiE bypass. |
| A write without a key/WHERE needs an observable refusal ([#3664](https://github.com/TableProApp/TablePro/issues/3664)). | UI affordances and driver helpers should not silently turn an unkeyed edit into a broad write. | BookiE already requires keys for generated grid updates and has `NoPrimaryKey` coverage. Preserve the contract across each mutation path and assert that refused writes never reach the driver. No concrete missing-key defect was confirmed here. |
| CTE and `ORDER BY` completion edge cases ([#3608](https://github.com/TableProApp/TablePro/issues/3608)). | Completion is a parser/context problem, especially with nested scopes and aliases, not just a keyword list. | BookiE uses tokenized SQL and schema-aware candidates, but the current tests do not visibly pin `AS MATERIALIZED`, data-modifying CTE `RETURNING`, `VALUES` CTE, nested `WITH`, or alias completion in `ORDER BY`. These are good focused UX regression candidates; they are not execution/parser correctness claims. |
| PostgreSQL local sockets and sequence management ([#3619](https://github.com/TableProApp/TablePro/issues/3619), [#3605](https://github.com/TableProApp/TablePro/issues/3605)). | Connection configuration and database-object browsing are distinct capabilities. | BookiE stores PostgreSQL socket-directory configuration and lists sequences in catalog metadata. That does not imply a sequence-management UI. Check the current connection UX before treating socket support as a gap; keep any sequence DDL/editor request separate from catalog listing. |
| Real SSH integration matrices ([#3662](https://github.com/TableProApp/TablePro/issues/3662)). | Unit mocks miss OpenSSH behavior, agent forwarding and algorithm/version interactions. | BookiE already has Docker-backed OpenSSH session tests, including an SSH-agent-held key and jump hosts, plus built-in-agent tests. TablePro's claim of no real agent test does not apply. Additional algorithm/version combinations may still be useful if supported by the SSH contract. |

## Failure patterns worth guarding against

- **A compatibility toggle can lie.** TablePro [#1247](https://github.com/TableProApp/TablePro/issues/1247) reports a TLS “skip verify” setting that still verified certificates. For BookiE, pair each TLS mode with both positive and negative certificate tests and verify the selected mode reaches every transport path. BookiE already has driver TLS and release tiers; this is a review checklist, not a confirmed defect.
- **Truncation must travel with the value.** TablePro [#1345](https://github.com/TableProApp/TablePro/issues/1345) and [#2012](https://github.com/TableProApp/TablePro/issues/2012) describe display/export paths that hid truncation or ignored limits. BookiE has bounded results and value/export contracts; keep truncation, row limits and incomplete-result state explicit in every consumer, including MCP.
- **Async work needs cancellation and identity.** TablePro [#2058](https://github.com/TableProApp/TablePro/issues/2058) and [#2059](https://github.com/TableProApp/TablePro/issues/2059) report superseded work continuing or leaking. BookiE's UI rules require cancellation to reach the operation and generation/request IDs to reject stale results. Apply both at each newly added load/search/query path.
- **Tests must not mutate a developer's real data.** TablePro [#2242](https://github.com/TableProApp/TablePro/issues/2242) reports a test writing into a user's audit data. BookiE's rule is isolated temporary state; preserve it for storage, audit and keyring fixtures.
- **Metadata is untrusted and scoped.** TablePro [#2934](https://github.com/TableProApp/TablePro/issues/2934) reports PostGIS resolution failing outside `public`; [#3103](https://github.com/TableProApp/TablePro/issues/3103) reports leaked metadata sessions. Test non-default schemas/search paths and ensure catalog sessions close on errors/cancellation.
- **UI state can be lost by a successful mutation.** TablePro [#3316](https://github.com/TableProApp/TablePro/issues/3316) reports save clearing filters/sort. BookiE already tracks row identity and grid state; regression tests should assert user-visible state survives edits where the contract says it should.
- **Port selection has a race.** TablePro [#216](https://github.com/TableProApp/TablePro/issues/216) is a useful SSH forwarding race example. BookiE's OpenSSH path selects a loopback port by bind/read/drop before asking SSH to forward it, so a TOCTOU window exists. The code sets `ExitOnForwardFailure` and checks the forwarding command before returning an endpoint, which appears fail-closed (availability failure if another process wins), not a demonstrated connection hijack. Add a deterministic test or retain as a reviewed limitation if this boundary changes.

## Not equivalent to BookiE

TablePro [#3658](https://github.com/TableProApp/TablePro/issues/3658) describes restoring several sessions, including disconnected or canceled entries. BookiE's current window model centers on one active connection; saved connections and per-connection workspace persistence are separate. Do not copy the multi-session strip behavior without a product decision.

## Suggested follow-up order

1. Use existing BookiE #580 for large-catalog latency and responsiveness acceptance.
2. Continue the already-recorded PostgreSQL extension qualification, starting with bounded pgvector decode/display and explicit refusal cases.
3. Add focused completion cases only when the editor UX work is scheduled.
4. Revisit SSH algorithm/version matrix breadth only when expanding the supported SSH contract.
5. Consider a supported-path CSV import/export integration scenario after full-table snapshot export is decided; do not broaden the current import/export promise by implication.

No BookiE issues were opened from this comparison: the clear catalog item is already tracked, extension work is already researched, and the remaining items are test proposals or need a confirmed reproduction and owner.
