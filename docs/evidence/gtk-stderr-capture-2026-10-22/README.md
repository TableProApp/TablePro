# GTK harness stderr capture, October 22

Issue [#1279](https://github.com/cozyGarage/BookiE/issues/1279) requires installed test stderr to remain drained or file-backed. The previous start_application helper spawned the app with stderr=PIPE and read it only during startup-failure cleanup or stop_application. An application producing more than pipe capacity could block before it exposed its expected window or completed a scenario.

A headless regression executes the actual helper functions with a synthetic child that writes 256 KiB of diagnostics before creating its readiness marker. With the old implementation, both success and nonzero-exit cases failed because the child could not finish writing. The first attempted regression had an incomplete AT-SPI stub; that setup error was corrected before the valid failing run.

The correction uses a temporary file for child stderr, seeks to its start after stopping the child, preserves the existing diagnostic return value, and closes the file. Four focused tests pass: large stderr without startup blockage, nonzero-exit diagnostics, spawn-failure cleanup, and missing-window cleanup. The existing two evidence-artifact tests also pass. No application behavior or logging configuration changes.

This independently reproduces a harness defect. It does not establish why the older Forgejo run 856 remained in its PostgreSQL GTK/SSH recovery scenario. The installed release binary passed `restart_restores_active_editor_and_connection` under private D-Bus and Xvfb using the changed harness: scenario 18.045 seconds, harness exit 0. The binary was the original Arch release executable, not a build of this test-only branch. Artifacts are under `/home/trung/bookie-test/release-0.2.0-bd31a1d8b/profiles/gtk-stderr-restart-smoke/`. A bus-disconnection message appeared during teardown after the scenario passed; no native desktop interaction was performed. Full preflight passed. A revised Forgejo gate remains pending; no new gate was started before the maintainer-requested pause.
