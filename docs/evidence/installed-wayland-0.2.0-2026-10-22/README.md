# Installed BookiE 0.2.0 native Wayland check

## Environment and package

The installed package was `bookie 0.2.0-1` on Arch Linux / Omarchy with Hyprland 0.56.2, GTK 4.24.1, libadwaita 1.10.0, GtkSourceView 5.22.0 and display scale 1. The app used native Wayland (`xwayland: false`). Package build inputs identify release commit `bd31a1d8b3dc83200c324b9f37fa83f3660d8aab` (`linux-v0.2.0`). `/usr/bin/bookie` SHA-256 was `d45556da8b994688987157cfc74e1d58e39d10894e11b157fc8077b2ccfbb386`. `pacman -Qkk bookie` reported 28 files with no altered files.

The repository checkout was `linux` at `faea584d1c151295583840c2af2d2467e7647c21`; this identifies the review context, not the installed binary source. The release source identity is recorded separately above.

## Observations

- The welcome screen and PostgreSQL connection form rendered. A local PostgreSQL 16.14 test container did not support TLS. The app's default Verify Full test correctly failed; selecting Disabled made the connection test pass. The test server bound to loopback only.
- A synthetic table with three rows showed primary-key marking, NULL separately from empty text, booleans, exact `numeric(24,6)` values, multiline text, Unicode edits and ellipsized long text. A SQL `UPDATE ... RETURNING` wrote and displayed the changed value. Timestamptz displayed the same instant normalized to `+00:00`; bytea appeared as `<4 bytes>`, arrays as `{"alpha","beta"}` and JSONB as `{"kind":"plain","count":1}`. Screenshots: `/tmp/bookie-installed-gtk-2026-10-21/postgres-connect-form.png`, `postgres-connect-result.png`, `postgres-grid-dark.png`, `table-filter-dark.png`.
- With the disposable PostgreSQL server paused, retrying the table read showed “Couldn't load rows” and “The operation timed out.” That is the expected result for the deliberately unavailable test server. During the same outage, clicking the database-switcher icon showed a narrow loading row with each character on a separate line. Accessibility reported the loading list item at 43×158 pixels and its label at 15×142. The subsequent error row was 44×1120, with a 16×302 label. Both are visibly broken layouts; the user screenshot and reproductions are `/tmp/codex-clipboard-whIFMb.png`, `/tmp/bookie-db-switcher-loading-repro.png` and `/tmp/bookie-db-switcher-error-repro.png`. The UI code sets a 280-pixel minimum content width, but the actual allocated rows did not honor it. Root cause is not established. After resuming the test server, the switcher listed `bookie_test` and `postgres` again. Retrying the row query then worked, matching the user’s report that the row-load retry behavior is correct. The test container was removed after verification.
- At 922 logical pixels wide, the 280-pixel sidebar remained open and reduced the content area. No literal sidebar/editor overlap appeared in the captured state. At 802 pixels, the sidebar collapsed automatically and Run/Split remained visible. With the row inspector hidden, the grid stayed usable and long values were ellipsized. At 1920 pixels, all six test columns were visible. Screenshots: `editor-dark-922px.png`, `editor-narrow-802.png`, `grid-narrow-802-no-inspector.png`, `editor-results-dark-full.png` in the temporary directory above. These observations do not rule out overlap in another view or with different content.
- The appearance selector was changed from System to Light to compare rendering, then restored to System and read back through the UI. The host prefers dark appearance, and BookiE rendered dark while set to System. High contrast, larger text, mixed-scale monitors and Orca remain untested.
- The test profile was removed through the saved-connection UI, including its keyring password. The disposable PostgreSQL container and its temporary environment file were also removed. During recovery, the accessibility tree continued to expose a `Connection lost — reconnecting` status with a zero-height allocation after the database list and row retry had recovered; a screenshot showed no visible banner. Treat that stale accessibility status as inconclusive, not as a confirmed user-visible issue.
- At 00:51:48 CEST, while the About and Preferences screens were being inspected, the installed `/usr/bin/bookie` process (PID 57076) aborted with `SIGABRT`. The terminal recorded GLib assertions in `g_variant_get_type_string` and `g_variant_new` (expected `(so)`, received null). GDB with Arch debuginfod symbols places the main thread in `abort`, GLib's `g_variant_new_va` / `g_variant_builder_add`, GTK's AT-SPI cache `handle_cache_method` while serving `GetItems`, GIO's idle D-Bus callback, and the GLib main loop before `g_application_run`. The failing GTK source frame is `gtk/a11y/gtkatspicache.c:300`, and the request came from D-Bus sender `:1.172`. This ties the abort to GTK constructing a response during an AT-SPI cache query. It does not establish whether GTK or BookiE supplied the invalid variant, nor whether the abort can occur without accessibility-tree inspection. The core remains under systemd-coredump; no extracted copy was retained. Other threads were mostly waiting in GLib, Pango and Radeon Vulkan/Gallium code. The crash happened after the test connection and container had been removed; no unsaved test edit or database data was lost. `free -h` immediately afterward showed 7.3 GiB available, and no kernel OOM event appeared in the crash-minute journal window. `coredumpctl list` also shows four earlier BookiE crashes from October 9–15 (SIGSEGV); their executable/build identities do not prove recurrence on this release binary.

## Resource sample

One synthetic query returned 100 rows, each containing an 8 KiB generated text value (`repeat('x', 8192)`). In this sample, output appeared in 2.69 seconds. Sampling only the BookiE PID recorded 243,144 KiB RSS before the query and 244,192 KiB peak/final RSS, with 1.76 seconds of CPU time. The 100 ms accessibility-tree polling used to detect completion adds measurement overhead. An earlier run recorded 0.67 seconds and about 189,648 KiB RSS in a different session; the values are not directly comparable. These are warm-session samples against a local container, not cold-start, sustained-load, large-dataset or comparative footprint benchmarks.

## Coverage limits

The 93-scenario installed GTK run under Xvfb/AT-SPI is recorded separately in [the 2026-10-21 GTK evidence](../installed-gtk-0.2.0-2026-10-21/README.md). This native run did not cover keyboard-only navigation across every dialog, clipboard round trips, Orca announcements, high contrast, SSH, other database engines, window restart restoration or long-duration memory behavior. The local PostgreSQL switcher recovery and test-resource cleanup were verified; broader live-server restart behavior remains untested. Screenshots and raw profiles are temporary under `/tmp/bookie-installed-gtk-2026-10-21/` and `/tmp/` and are not committed. The current native test session was interrupted by the 00:51:48 CEST abort during AT-SPI tree inspection and needs a clean relaunch before further GUI checks. Avoid AT-SPI queries during the next visual-only pass; this isolates ordinary interaction from the observed trigger path but does not resolve the crash cause.
