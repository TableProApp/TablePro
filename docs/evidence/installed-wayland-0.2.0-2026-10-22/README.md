# Installed BookiE 0.2.0 native Wayland check

## Environment and package

The installed package was `bookie 0.2.0-1` on Arch Linux / Omarchy with Hyprland 0.56.2, GTK 4.24.1, libadwaita 1.10.0, GtkSourceView 5.22.0 and display scale 1. The app used native Wayland (`xwayland: false`). Package build inputs identify release commit `bd31a1d8b3dc83200c324b9f37fa83f3660d8aab` (`linux-v0.2.0`). `/usr/bin/bookie` SHA-256 was `d45556da8b994688987157cfc74e1d58e39d10894e11b157fc8077b2ccfbb386`. `pacman -Qkk bookie` reported 28 files with no altered files.

The repository checkout was `linux` at `faea584d1c151295583840c2af2d2467e7647c21`; this identifies the review context, not the installed binary source. The release source identity is recorded separately above.

## Observations

- The welcome screen and PostgreSQL connection form rendered. A local PostgreSQL 16.14 test container did not support TLS. The app's default Verify Full test correctly failed; selecting Disabled made the connection test pass. The test server bound to loopback only.
- A synthetic table with three rows showed primary-key marking, NULL separately from empty text, booleans, exact `numeric(24,6)` values, multiline text, Unicode edits and ellipsized long text. A SQL `UPDATE ... RETURNING` wrote and displayed the changed value. Timestamptz displayed the same instant normalized to `+00:00`; bytea appeared as `<4 bytes>`, arrays as `{"alpha","beta"}` and JSONB as `{"kind":"plain","count":1}`. Screenshots: `/tmp/bookie-installed-gtk-2026-10-21/postgres-connect-form.png`, `postgres-connect-result.png`, `postgres-grid-dark.png`, `table-filter-dark.png`.
- With the disposable PostgreSQL server paused, retrying the table read showed “Couldn't load rows” and “The operation timed out.” That is the expected result for the deliberately unavailable test server. During the same outage, clicking the database-switcher icon showed a narrow loading row with each character on a separate line. Accessibility reported the loading list item at 43×158 pixels and its label at 15×142. The subsequent error row was 44×1120, with a 16×302 label. Both are visibly broken layouts; the user screenshot and reproductions are `/tmp/codex-clipboard-whIFMb.png`, `/tmp/bookie-db-switcher-loading-repro.png` and `/tmp/bookie-db-switcher-error-repro.png`. The UI code sets a 280-pixel minimum content width, but the actual allocated rows did not honor it. Root cause is not established. After resuming the test server, the switcher listed `bookie_test` and `postgres` again. Retrying the row query then worked, matching the user’s report that the row-load retry behavior is correct. The test container was removed after verification.
- At 922 logical pixels wide, the 280-pixel sidebar remained open and reduced the content area. No literal sidebar/editor overlap appeared in the captured state. At 802 pixels, the sidebar collapsed automatically and Run/Split remained visible. With the row inspector hidden, the grid stayed usable and long values were ellipsized. At 1920 pixels, all six test columns were visible. Screenshots: `editor-dark-922px.png`, `editor-narrow-802.png`, `grid-narrow-802-no-inspector.png`, `editor-results-dark-full.png` in the temporary directory above. These observations do not rule out overlap in another view or with different content.
- The installed binary also passed `mysql_unparseable_routine_dialog_denial_preserves_database` 1/1 in the isolated GTK harness against a temporary MySQL 8.0 container. Denying `CREATE PROCEDURE` left the server unchanged; approving the same unparseable statement created the procedure. The scenario took 7.302 seconds; total harness wall time was 21.86 seconds, sampled aggregate test-process-group CPU was 1.24 seconds and sampled peak aggregate RSS was 206,200 KiB across BookiE, the harness, Xvfb and D-Bus. The temporary container was removed by the harness, and `docker ps` was empty afterward. No later BookiE core dump was found. Artifacts: `/tmp/bookie-gtk-mysql-approval-20261022/`.
- Two more installed-binary scenarios passed 1/1 each against a disposable MySQL 8.0 container: `mysql_grid_edit_and_delete_commit_to_the_server` (7.562 seconds) and `mysql_enum_set_grid_edit_preserves_native_values_and_siblings` (7.497 seconds). The server confirmed committed row edit/delete behavior and that ENUM/SET edits preserve SQL NULL, empty values, literal `NULL`, and sibling rows. The SET edit preserved declared member order (`read,write`). Whole harness wall time was 27.95 seconds, sampled aggregate test-process-group CPU was 1.89 seconds, and sampled peak aggregate RSS was 205,936 KiB across BookiE, the harness, Xvfb and D-Bus. The fixture container was removed and no new core dump appeared. At 01:08:23 CEST, the visible native process remained alive at 99,188 KiB RSS and 0.0% average CPU after 11 minutes 20 seconds of uptime. Artifacts: `/tmp/bookie-gtk-mysql-grid-20261022/`.
- The installed binary passed the MongoDB 7 cursor/edit scenario 1/1. A server-side name change stayed invisible in the loaded cursor until refresh; after refresh, a client edit stayed local until approval, then updated only the name and preserved the sibling field. Scenario time was 7.015 seconds; total harness wall time was 12.05 seconds, sampled aggregate test-process-group CPU was 1.02 seconds and sampled peak aggregate RSS was 215,960 KiB. The temporary container was removed and no core dump appeared. Artifacts: `/tmp/bookie-gtk-mongodb-20261022/`.
- The installed binary passed the ClickHouse 24.8 Enum8/Enum16 grid scenario 1/1. It changed the boundary labels from `low8`/`low16` to `high8`/`high16`, then verified those native labels and untouched literal `NULL`, SQL NULL, empty labels and sibling rows at the server. Scenario time was 5.635 seconds; total harness wall time was 11.44 seconds, sampled aggregate test-process-group CPU was 0.78 seconds and sampled peak aggregate RSS was 206,720 KiB. The temporary container was removed and no core dump appeared. Artifacts: `/tmp/bookie-gtk-clickhouse-20261022/`.
- The saved SQL Server read-only profile initially failed while its original fixture was stopped. The old fixture container had exited with code 255 on 2026-09-26; its log showed SQL Server had reached ready state before it stopped. A new project using the repository's documented manual fixture then became healthy, and its init job created `dbo.people` with two rows. The installed native Wayland app connected from the saved profile and rendered `dbo.people`, both rows, the row count (`Rows 1 – 2 of 2`) and the SQL Server header. The header omitted a server version, so that part of the broader saved-connection check remains unverified. The app observer ran for 60.43 seconds, during which the BookiE process CPU time increased by 18.58 seconds and peak RSS was 135.2 MiB. The observer repeatedly traversed the AT-SPI tree and did not stop when success appeared, so these resource numbers are instrumentation-heavy and the 60.43-second window is not a connection-latency measurement. The isolated fixture and its volume were removed afterward; the older fixture was left untouched. No repository test or source code changed.
- Six installed-binary PostgreSQL 17 scenarios passed 1/1: browse rows and values (5.864 seconds), hidden-projection refresh/edit (11.724), grid edit/delete (7.747), enum preservation (7.922), database switch/reconnect (3.472), and session commit recovery after an aborted statement (11.038). The session case rolled back the unrecovered aborted transaction and committed the savepoint-recovered transaction with the expected row counts. Total harness wall time was 54.54 seconds, sampled aggregate test-process-group CPU was 7.26 seconds and sampled peak aggregate RSS was 207,524 KiB. The temporary database container was removed and no core dump appeared. These runs also logged the `AdwToolbarView` width warning at 964–976 px requested versus 910 px available, plus a non-fatal GDK frame-timing warning. Artifacts: `/tmp/bookie-gtk-postgres-20261022/`.
- The MySQL and PostgreSQL editor runs logged `AdwToolbarView` requesting 964–976 px while its `AdwBreakpointBin` had 910 px available. The same width warning appears in 13 of the 93 saved scenario stderr files from the previous installed GTK run. The matching source widget is the SQL editor toolbar. This confirms a repeated minimum-width warning in the Xvfb layout, but does not by itself prove visible clipping. The native 922 px and 802 px screenshots above show Run and Split visible without literal sidebar overlap; keyboard or mouse activation at those sizes and the 900–964 px range remain untested. This is an unresolved responsive-layout signal, not a confirmed native Wayland defect.
- The appearance selector was changed from System to Light to compare rendering, then restored to System and read back through the UI. The host prefers dark appearance, and BookiE rendered dark while set to System. High contrast, larger text, mixed-scale monitors and Orca remain untested.
- The test profile was removed through the saved-connection UI, including its keyring password. The disposable PostgreSQL container and its temporary environment file were also removed. During recovery, the accessibility tree continued to expose a `Connection lost — reconnecting` status with a zero-height allocation after the database list and row retry had recovered; a screenshot showed no visible banner. Treat that stale accessibility status as inconclusive, not as a confirmed user-visible issue.
- At 00:51:48 CEST, while the About and Preferences screens were being inspected, the installed `/usr/bin/bookie` process (PID 57076) aborted with `SIGABRT`. The terminal recorded GLib assertions in `g_variant_get_type_string` and `g_variant_new` (expected `(so)`, received null). GDB with Arch debuginfod symbols places the main thread in `abort`, GLib's `g_variant_new_va` / `g_variant_builder_add`, GTK's AT-SPI cache `handle_cache_method` while serving `GetItems`, GIO's idle D-Bus callback, and the GLib main loop before `g_application_run`. The failing GTK source frame is `gtk/a11y/gtkatspicache.c:300`, and the request came from D-Bus sender `:1.172`. This ties the abort to GTK constructing a response during an AT-SPI cache query. It does not establish whether GTK or BookiE supplied the invalid variant, nor whether the abort can occur without accessibility-tree inspection. The core remains under systemd-coredump; no extracted copy was retained. Other threads were mostly waiting in GLib, Pango and Radeon Vulkan/Gallium code. The crash happened after the test connection and container had been removed; no unsaved test edit or database data was lost. `free -h` immediately afterward showed 7.3 GiB available, and no kernel OOM event appeared in the crash-minute journal window. `coredumpctl list` also shows four earlier BookiE crashes from October 9–15 (SIGSEGV); their executable/build identities do not prove recurrence on this release binary.
- The installed `/usr/bin/bookie` binary then passed `restart_restores_active_editor_and_connection` 1/1 in the isolated GTK harness using a private D-Bus session, Xvfb, and a temporary SQLite profile. The test restored the active connection and editor draft, restored the kept table tab, omitted the preview tab, left the draft unexecuted until Run, then verified the insert. Scenario time was 15.787 seconds; whole harness wall time was 19.41 seconds, sampled aggregate test-process-group CPU was 1.08 seconds, and sampled peak aggregate RSS was 203,260 KiB across BookiE, the harness, Xvfb and D-Bus. The app emitted a non-fatal GDK frame-timing warning. The wrapper printed `A connection to the bus can't be made` during teardown after the scenario passed; the harness exited 0. The clean run used loopback MCP port 37241; its artifacts are in `/tmp/bookie-gtk-restart-clean-20261022/`. No later BookiE core dump was found. This is installed-binary Xvfb evidence, not native Wayland interaction.

## Resource sample

One synthetic query returned 100 rows, each containing an 8 KiB generated text value (`repeat('x', 8192)`). In this sample, output appeared in 2.69 seconds. Sampling only the BookiE PID recorded 243,144 KiB RSS before the query and 244,192 KiB peak/final RSS, with 1.76 seconds of CPU time. The 100 ms accessibility-tree polling used to detect completion adds measurement overhead. An earlier run recorded 0.67 seconds and about 189,648 KiB RSS in a different session; the values are not directly comparable. These are warm-session samples against a local container, not cold-start, sustained-load, large-dataset or comparative footprint benchmarks.

After relaunching the installed app at 00:57 CEST, an idle sample at 00:59:43 CEST showed 99,140 KiB RSS and 0.2% average CPU over 2 minutes 40 seconds (`ps`). This is a single idle observation, not a steady-state or cross-client benchmark. No additional BookiE core dump was listed between the earlier 00:51:48 abort and this sample.

A follow-up sample at 01:03:26 CEST, after 6 minutes 23 seconds of process uptime and including the isolated scenario run, showed 99,156 KiB RSS and 0.1% average CPU for the visible native Wayland process. RSS remained near the previous idle sample; this short interval does not establish long-duration behavior.

At 01:12:29–01:12:49 CEST, the native process RSS held at 112,624 KiB across five samples; CPU time increased by 0.03 seconds over 20 seconds. This is about 13 MiB above the 01:08:23 sample, but it did not continue rising during this window. The cause of that step increase is not isolated, so this does not establish a leak or a long-duration memory trend.

## Coverage limits

The 93-scenario installed GTK run under Xvfb/AT-SPI is recorded separately in [the 2026-10-21 GTK evidence](../installed-gtk-0.2.0-2026-10-21/README.md). This native run did not cover keyboard-only navigation across every dialog, clipboard round trips, Orca announcements, high contrast, SSH, other database engines or long-duration memory behavior. The local PostgreSQL switcher recovery and the MSSQL saved-profile connection were verified; broader live-server restart behavior remains untested. Screenshots and raw profiles are temporary under `/tmp/bookie-installed-gtk-2026-10-21/` and `/tmp/` and are not committed. A previous native test session was interrupted by a 00:51:48 CEST abort during AT-SPI tree inspection. The later SQL Server tree query succeeded, but this does not resolve the GTK/AT-SPI crash cause. Use visual-only checks where possible to avoid that observed trigger path.
